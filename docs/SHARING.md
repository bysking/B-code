# 从零实现一个 Claude Code：B Code 的架构与原理

> 面向：想搞懂「AI Agent CLI 到底怎么跑起来的」的你。
> 不需要读源码，跟着往下看就行。

---

## 0. 先说清楚：这类工具有什么用

你可能用过 ChatGPT 网页版：你问它问题，它回答你。但你让它「修一下这个 bug」，它只能给你一段代码，**你自己去复制、粘贴、保存、跑测试**。

Claude Code 这类工具改变的是最后一步——它**自己动手**：

```
你：这个项目的测试挂了，帮我看看
它：（读 package.json）→（跑 bun test）→（读报错的那个文件）→（改代码）→（再跑测试）→ 通过了
```

区别不在「AI 更聪明了」，而在于**它长出了手**：能读文件、能改文件、能执行命令。并且——这一点最关键——**它知道自己刚刚做了什么**，能根据结果决定下一步。

这篇文档讲的就是：这只「手」是怎么造出来的。

---

## 1. 第一性原理：Agent 与聊天机器人的唯一区别

先看这个循环，它是**全部**的核心：

```
         ┌─────────────────────────┐
         │      1.把消息发给模型     │
         └───────────┬─────────────┘
                     ↓
         ┌─────────────────────────┐
         │  2.模型决定要不要用工具    │
         └───────────┬─────────────┘
                     ↓
            ┌────────┴────────┐
         2.1 要用工具        2.2 不用工具
            ↓                 ↓
    3.执行工具、结果喂回      4.任务结束，把
    （回到最上面:1）         回答交给用户(结束)
```

**就这么简单。** 整个 B Code 有约 1.2 万行业务代码（不含测试），但这四行就是它的心脏。

用伪代码写出来是：

```
while (true) {
  回复 = 模型调用(历史消息, 可用工具清单) // 传入上下文作为模型参数，历史消息是一个数组
  if (回复里没有工具调用) break     // 模型认为完事了
  结果 = 执行工具(回复里的工具调用名字) // 读支持多个，写只能串行等待
  历史消息.push(结果)               // 把结果变成下一轮的输入
}
```

### 为什么这个循环是分界线

**决定循环转不转的，是模型，不是代码。** 这句话值得多想一下。

传统程序：`if 文件不存在 then 创建文件` —— 分支是程序员写死的。
Agent：下一步做什么，是模型读完上一步的结果后**现场决定**的。代码只提供「能做什么」的清单，不规定「先做什么后做什么」。

所以：

- 你没法预测它会调几次工具（可能 2 次，可能 20 次）
- 你没法用测试断言「一定走了某条路径」
- 但正因如此，它能处理你没预设过的情况

理解了这一条，后面所有模块的存在理由都清楚了：**它们全都在解决「这个循环在真实世界里会遇到什么问题」**。

## 2. 循环转起来需要的三样东西

回到上面那个伪代码，你会发现它引用了三个还不存在的东西：


| 伪代码里的东西  | 回答什么问题                 | 对应模块                     |
| ----------------- | ------------------------------ | ------------------------------ |
| `模型(...)`     | 怎么跟大模型说话？           | 后端层（backend）            |
| `可用工具清单`  | 怎么让模型知道它能干什么？   | 工具系统（registry + tools） |
| `执行工具(...)` | 调用真的执行时怎么保证安全？ | 权限系统（permissions）      |

下面逐个展开。

---

## 3. 模块一：怎么跟模型说话（后端层）

### 要解决的第一个问题：换个模型就得改全部代码

最直觉的写法是把 SDK 调用直接写在循环里。但很快会遇到问题：

- 今天用 Anthropic，明天想用 DeepSeek（OpenAI 兼容格式）
- 两家的消息格式、工具定义格式**不一样**

如果让循环直面两套格式，循环里就会长满 `if (是Anthropic) {...} else {...}`，越写越乱。

### 做法：内部只认一种形状，在边界处翻译

B Code 的选择是：**内部所有代码只认 Anthropic 的消息格式**，OpenAI 兼容的后端在最后一步做格式转换。

```
    Agent 循环（只认一种格式）
            ↓
    ┌───────┴───────┐
 Anthropic 后端   OpenAI 兼容后端
    ↓                 ↓
  原样发送        转换成 OpenAI 格式
```

**带来的好处**：主循环完全不知道后端是谁，加第三个后端不用碰循环一行代码。

#### 两套格式的核心字段对照

先说结论：**差异不在"消息内容"，而在"工具调用放在哪儿"**。普通文本对话两家几乎一样，一旦涉及工具就开始分叉。

**Anthropic：工具是 content 里的一种块**

```json
{
  "system": [{ "type": "text", "text": "你是..." }],
  "tools": [
    { "name": "read_file", "description": "...", "input_schema": { "type": "object" } }
  ],
  "messages": [
    { "role": "user", "content": "读一下 a.txt" },
    {
      "role": "assistant",
      "content": [
        { "type": "text", "text": "我来读。" },
        { "type": "tool_use", "id": "toolu_1", "name": "read_file", "input": { "path": "a.txt" } }
      ]
    },
    {
      "role": "user",
      "content": [
        { "type": "tool_result", "tool_use_id": "toolu_1", "content": "文件内容..." }
      ]
    }
  ]
}
```

**OpenAI 兼容：工具是 assistant 上的独立字段，结果单独成一条消息**

```json
{
  "messages": [
    { "role": "system", "content": "你是..." },
    { "role": "user", "content": "读一下 a.txt" },
    {
      "role": "assistant",
      "content": "我来读。",
      "tool_calls": [
        {
          "id": "call_1",
          "type": "function",
          "function": { "name": "read_file", "arguments": "{\"path\":\"a.txt\"}" }
        }
      ]
    },
    { "role": "tool", "tool_call_id": "call_1", "content": "文件内容..." }
  ]
}
```

逐条对应关系（这就是 `toOpenAIMessages` / `fromOpenAIResponse` 干的事）：


| 概念           | Anthropic                                                   | OpenAI 兼容                                         |
| ---------------- | ------------------------------------------------------------- | ----------------------------------------------------- |
| system         | 顶层 `system` 参数，支持多块                                | `messages` 里的 `role: "system"`                    |
| 工具清单       | `{ name, description, input_schema }`                       | `{ type: "function", function: { … parameters } }` |
| 工具调用       | assistant `content` 里的 `tool_use` 块                      | assistant 消息上的 `tool_calls` 数组                |
| 调用参数       | `input`：**已解析的对象**                                   | `arguments`：**JSON 字符串**（流式下还是分片拼的）  |
| 工具结果       | user `content` 里的 `tool_result` 块，用 `tool_use_id` 关联 | 独立的 `role: "tool"` 消息，用 `tool_call_id` 关联  |
| 一条 user 消息 | 可同时含 text + image + tool_result                         | 必须拆开：内容走 `user`，结果走 `tool`              |
| 结束原因       | `stop_reason`                                               | `finish_reason`                                     |

这里有两个最容易踩的坑：

1. **`arguments` 是字符串不是对象**。所以转过去要 `JSON.stringify(input)`，转回来要 `JSON.parse(arguments)`；解析失败时必须兜底成空对象，否则一次坏参数就让整个循环崩掉。
2. **消息条数会变**。Anthropic 侧一条 user 消息塞了 3 个 `tool_result`，到了 OpenAI 侧就裂成 3 条 `role: "tool"` 消息。所以「消息数量」在两套格式里根本对不上，做历史压缩或 token 计数时不能按条数换乘。

**这也解释了为什么值得在内部固定一种形状**：如果两套格式直接进主循环，上面这些坑就会散布在循环、上下文压缩、会话存储等每一处；固定在 Anthropic 形状后，全部差异被压缩到两个纯函数里（可单独测试，事实也确实如此）。


## 4. 模块二：工具系统 —— 让模型知道它能干什么

### 核心设计：注册表

模型不是「知道」它能读文件，而是**我们在每次请求里告诉它一份清单**：

```
可用工具：
  - read_file: 读文件内容
  - write_file: 写文件
  - edit_file: 精确替换文件片段
  - list_files: 列目录
  - grep_search: 搜索代码
  - run_shell: 执行命令
  - ...
```

每个工具都声明：叫什么名字、干什么用、**需要什么参数**（JSON Schema 格式）。

模型返回的就是符合这个 schema 的结构化数据，而不是自然语言。这样代码才能可靠地解析和执行。

### 为什么没有「删文件」工具

这是一个容易被忽略但很说明问题的设计。B Code 的工具清单是：


| 工具           | 用途                              | 权限档位  |
| ---------------- | ----------------------------------- | ----------- |
| `read_file`    | 读文件                            | 只读      |
| `file_content` | 按需取回已读文件 / 探测是否被改动 | 只读      |
| `list_files`   | 列目录                            | 只读      |
| `grep_search`  | 全文搜索（**会读 `.gitignore`**） | 只读      |
| `write_file`   | 写文件                            | 写        |
| `edit_file`    | 精确替换片段                      | 写        |
| `run_shell`    | 执行命令                          | 执行      |
| `ask_user`     | 向用户提问（选项 / 文本）         | 自授权    |
| `todo_write`   | 维护任务清单                      | 写        |
| `save_memory`  | 存一条长期记忆                    | 写        |
| `write_plan`   | 写计划文件                        | plan 专用 |
| `agent`        | 派子 Agent 调研                   | 只读      |
| `review_plan`  | 派子 Agent 对抗性审查计划         | 只读      |

**注意没有 `delete_file`。** 删除只能通过 `run_shell` 执行 `rm`——而 `rm` 会被**按目标分级**：`rm -rf /`、`rm -rf ~` 这类灾难目标直接拒绝（任何模式都拦），`rm -rf dist`、`rm -rf node_modules` 这类日常清理只需确认一次，授权后可持久化免问。

这个设计的意思是：**把「不可逆操作」全部收拢到唯一一条需要过权限的通道上**。如果单独开一个 `delete_file` 工具，就等于多开了一扇需要单独设防的门。

同理 `grep_search` 会读 `.gitignore`：否则 `node_modules`、`dist`、`*.log` 会被一起搜出来，既污染结果又白烧 token。

### 为什么 `edit_file` 比「重写整个文件」重要

`write_file` 是最直觉的做法：把整个文件内容重新写一遍。但问题很明显——

- 一个大文件几百行，每次改一行就重传全文，token 成本极高
- 模型很难一字不差地重述整个文件，容易把不相干的地方改掉

`edit_file` 只传「把这段原文替换成这段新文」。省 token，且改动范围天然受控。

### 关键洞察：MCP 工具和内置工具没有区别

MCP（Model Context Protocol）是一个「给模型接外部工具」的标准协议。你可以把它理解成「AI 工具界的 USB 接口」——别人写好的工具（比如连数据库、查文档、操作浏览器），通过这个协议就能接进来。

B Code 的设计是：**MCP 工具接进来后，和内置工具走完全一样的路径**——都是「名字 + schema + 执行函数」，都挂在同一个注册表里。

所以对循环来说，`read_file` 和 `mcp__github__create_issue` 没有任何区别。这是「注册表」这个抽象带来的直接好处。

### SDK 替你做了什么（以 `@modelcontextprotocol/sdk` 为例）

上面那个 USB 比喻要补一句：**协议本身不含任何工具逻辑**，它只规定"两端怎么把话说清楚"。官方 SDK 就是这套规定的实现，相当于 USB 控制器芯片。它包了五件事：

| SDK 负责 | 具体是什么 | 不做会怎样 |
|---|---|---|
| JSON-RPC 收发 + 请求配对 | 分配请求 id、把响应匹配回对应的 Promise、超时 reject | 自己维护一张并发请求的 id 映射表 |
| 握手与能力协商 | 自动 `initialize` 交换版本和能力清单，之后**按对方声明拦截不该发的请求** | 对不支持的工具发请求，永远等不到回包 |
| 能力 API + schema 校验 | `listTools` / `callTool` / `listResources` / `listPrompts` 等方法，返回值按 schema 校验成类型化对象 | 手写每个方法的报文构造和解析 |
| Transport 抽象 | 统一成 `start/send/close/onmessage` 四个方法，另有 stdio / Streamable HTTP / SSE / WebSocket 四种现成实现 | 每种通信方式各写一套 |
| 反向调用通道 | server 也能反过来求 client（借模型推理、问可访问目录、要用户填参数） | 只能单向调用 |

**握手那件事值得单独说**。`connect()` 内部会自动跑一遍：

```
client → server:  协议版本 + 我支持的能力
server → client:  协议版本 + 我提供的能力
client → server:  initialized（握手完成）
```

之所以要交换能力，是为了**双方各自降级**。B Code 在这件事上有条明确的原则：**宿主没注入的能力就绝不声明**——server 据此知道"这个客户端做不到"，自己就不发这类请求了；反过来若声明了却没人处理，就成了一个永远超时的坑。

**USB 比喻的边界**：SDK 是控制器芯片，不是设备驱动。它保证"话能说清楚"，至于 server 那边连的是数据库还是浏览器，SDK 一概不管——那正是 MCP 能让任意工具接进来的原因。

### 要解决的陷阱：工具结果把上下文撑爆

假设模型让你 `cat` 一个 10 万行的日志文件。这个结果如果原样塞回历史，**单次就吃掉了大半上下文窗口**，后面的对话全都没空间了。

三层防御：


| 层次   | 做法                                               | 解决什么             |
| -------- | ---------------------------------------------------- | ---------------------- |
| 第一层 | 单次结果超 5 万字符就截断（保留头尾，中间标省略）  | 单条结果不会失控     |
| 第二层 | 文件读一次后缓存，再读只返回指针（路径+行数+hash） | 同一文件不重复占空间 |
| 第三层 | 整体超阈值就压缩旧消息                             | 长对话能一直进行下去 |

**第二层特别值得说**——它解决的是「压缩导致模型失忆」这个连锁问题。

想象一下：模型读了 `auth.ts`，然后对话太长触发了压缩，旧消息被摘要掉了，`auth.ts` 的内容也跟着没了。模型想改这个文件，只好再读一遍。读一遍又占空间，又触发压缩……**死循环**。

B Code 的做法是：文件内容不放在消息历史里（历史里只有一个指针），实际内容存在会话级的缓存中。压缩时生成一份「已读文件索引」，告诉模型「这些文件你读过，需要时用 `file_content` 按需取」。

这样压缩**不会造成信息丢失**，因为权威数据在磁盘和缓存里，不在历史里。

## 5. 模块三：权限系统 —— 这是最需要敬畏的部分

### 为什么这个模块比看起来重要得多

一个能执行 `rm -rf /` 的 AI，和一个只能聊天的 AI，风险等级完全不同。

想象你半夜让 Agent 自主干活（这个功能真的有，见第 8 节），它理解错了你的意图，然后执行了 `sudo rm -rf /`……

**这个模块是 B Code 存在的必要条件。** 没有它，其他所有功能都不能给真人用。

### 四种模式：把「信任程度」变成一个显式的选择


| 模式        | 遇到文件写 / 命令执行时    | 适合什么时候用               |
| ------------- | ---------------------------- | ------------------------------ |
| **default** | 每次都问你                 | 日常使用（默认）             |
| **plan**    | **全部拦截**，只能读       | 让它先出方案，你确认后再执行 |
| **auto**    | 用一个 AI 分类器代替你判断 | 你信任它，但还想留一道保险   |
| **bypass**  | 不问，直接干               | 完全信任 / 沙箱环境          |

### 最重要的设计原则：危险命令任何模式都拦得住

这是整个系统里我认为最值得强调的一条：

```
危险命令清单（固定 9 条）
        ↓
   无论 default / plan / auto / bypass
        ↓
      直接拒绝，没有例外
```

清单是**固定枚举**的，不是「模型判断危险不危险」：


| 命令                  | 为什么不可逆           |
| ----------------------- | ------------------------ |
| `git reset --hard`    | 丢弃未提交改动         |
| `sudo`                | 提权，后续命令不再受控 |
| `mkfs`                | 格式化磁盘             |
| `> /dev/裸设备`       | 直接写设备             |
| `dd`                  | 磁盘级操作             |
| `kill`                | 杀进程                 |
| `reboot` / `shutdown` | 关机重启               |

注意 `rm` **不在这一档**——它的破坏力取决于**目标**，见下面「rm 为什么按目标分级」。

**为什么用固定清单而不是 AI 判断？** 因为这是**安全边界**，不能有概率。AI 判断有误判率，而这里需要的是「100% 确定」。清单的代价是会漏一些新型危险命令，所以还有下面要说的 fail-closed 兜底。

**为什么 `kill`/`dd`/`sudo` 要算「命令边界」？** 因为直接匹配会误杀——`npm run kill-port`、`dd-utils`、`git commit -m "add sudo docs"` 这类正常命令会被拦。所以规则改成「必须以它开头，或在 `;` `&` `|` 之后出现」，也就是真正的命令位置。同理 `> /dev/` 必须排除 `/dev/null`——丢 stderr 是最常见的降噪习惯，一刀切会把只读命令全拦掉。

**`--yolo`（bypass 模式）也拦不住它们。** 这不是疏忽，是刻意的。因为这类命令**不可逆**——问不问用户是关于「效率」的取舍，但有些操作一旦执行就没法挽回，那就不该给任何模式开绿灯。

### rm 为什么按目标分级

`rm -rf` 的破坏力不来自 `-rf` 这两个字母，而来自它后面跟的**目标**。一刀切 deny 有两个后果：一是模型永远清不掉构建产物（本项目刻意不提供 `delete_file`，删除只能走 shell，等于砍掉一种能力）；二是只匹配字面 `rm -rf` 拦不住变体——`-fr`、`-r -f`、`-Rf`、`--recursive --force` 全都能绕过。既漏又严。

所以改成先归一见选项，再看目标：

| 目标                                                       | 判定      |
| ---------------------------------------------------------- | --------- |
| `/`、`~`、`*`、`.`、`..`、`$HOME`、顶层目录、当前工作目录   | `deny`    |
| 项目内路径、`/tmp`、`node_modules`/`dist`/`build`          | `confirm` |

提不出目标时（如 `bash -c "rm -rf /"` 这类嵌套 shell）按最坏情况算 `deny`。`confirm` 档走的是 ⑤ 的常规流程，确认一次即可持久化免问。

### 判定顺序（顺序本身就是设计）

```
① 危险命令？        → 拒绝（最高优先级，任何模式）
①' rm 灾难目标？    → 拒绝；其余目标落到 ⑤
② plan 模式？       → 非只读操作一律拒绝
③ 只读操作？        → 放行（读文件不需要打扰用户）
④ 敏感命令？        → 必须确认（如 git push，但用户可授权「以后别问」）
⑤ 其他             → 必须确认（fail-closed）
```

**注意 ④ 和 ⑤ 的区别**：`git push` 属于「敏感但可商量」——它不是不可逆操作（提交还在本地），所以允许用户授权后免问。而危险清单里那些是「不可逆」，没有商量余地。

**注意 ⑤ 的用词：fail-closed（默认拒绝）。**

意思是：如果一个工具**没有声明自己属于哪一类**（比如未来新接入的 MCP 工具，或者别人写的插件），系统默认**要求确认**，而不是默认放行。

这个选择很关键。反过来（fail-open）会让新工具自动获得权限——一个恶意的 MCP server 接进来就能随便读你的文件。安全的默认值必须是「不确定就拦」。

### 白名单：怎么避免把用户烦死

如果每写一个文件都要确认，用 10 分钟用户就疯了。

B Code 有白名单机制，但有四条**准入规则**，只有满足才允许「永久记住」：


| 规则                       | 原因                             |
| ---------------------------- | ---------------------------------- |
| 长度不超过 200 字符        | 超长命令几乎必然是一次性脚本     |
| 不含 inline 脚本 / heredoc | 内容每次都不同，记住也没用       |
| 命令做归一化（折叠空白）   | 否则格式抖动会造出一堆近似重复项 |
| 条目数封顶，超出淘汰最旧   | 防止配置文件无限膨胀             |

这里的设计哲学是：**持久化白名单应该沉淀「可复用的能力」，而不是「一次性的具体调用」**。`bun test` 值得记住，`node -e "console.log(123)"` 不值得。

## 7. 痛点一：同样的指令，Agent 表现不稳定

### 问题

你让它修 bug，它的第一反应是直接改代码——但它**根本没读过那个文件**，改出来的东西语法都不对。

### 原因

模型的行为很大程度上由 **system prompt**（系统提示）决定。没有约束的话，它倾向于「快速给出答案」而不是「先看清楚再动手」。

### 做法：两段式 System Prompt

B Code 的 system prompt 分成两块：

```
┌────────────────────────────────────┐
│ 静态核心：行为准则                  │  ← 一字不变，可被缓存
│  - 没读过的文件不许改               │
│  - 优先用专用工具而不是 shell       │
│  - 保持回答简短                     │
│  - 危险操作先确认                   │
├────────────────────────────────────┤
│ 动态上下文：当前环境的快照           │  ← 每次重建
│  - 工作目录 / 平台                 │
│  - Git 分支、未提交改动             │
│  - 项目说明（CLAUDE.md）           │
│  - 相关记忆、可用技能               │
└────────────────────────────────────┘
```

**为什么要分成两段？** 因为成本。

大模型 API 对「完全相同的前缀」有**缓存折扣**——命中缓存的部分只按约 1/10 价格计费。静态核心跨会话逐字不变，所以能被缓存；如果把动态内容（每次都变）混在前面，缓存就永远打不中。

一个长会话里，这个差别是**几倍的成本差距**。

**为什么动态内容放最后？** 有个心理学现象叫「近因效应」——模型对**末尾**的内容注意力更高。把最新的环境信息、记忆、技能放在最后，它们对当轮决策的影响更大。

## 8. 痛点二：上下文总会满

### 问题

聊了 40 轮之后，程序报错：上下文超长。

### 原因

模型有上下文窗口上限。历史消息只增不减，撞墙是必然的。

### 做法：分级压缩

不是「满了再处理」，而是**从轻到重的多道防线**：

```
第 0 层：单条工具结果超 5 万字符      → 截断
第 1 层：同一文件重复读              → 只返指针
第 2 层：消息条数超 45 或 token 超预算 → 用模型摘要旧消息
```

第 2 层（压缩）的具体做法：

```
压缩前：[消息1][消息2]...[消息40][消息41][42][43][44][45]
                          ↓ 旧消息摘要成一段
压缩后：[摘要：前面处理了xxx，读了这些文件...][41][42][43][44][45]
                                              └── 最近 5 条原样保留
```

**为什么保留最近 5 条？** 因为最近的对话是「当前正在做的事」，摘要会丢失细节（具体的行号、函数名）。而压缩的目的只是腾空间，不是遗忘——所以正在处理的部分必须保持原样。

**为什么阈值是窗口的 40% 而不是 90%？** 两个原因：

1. token 是按字符估算的，中文/代码的估算是**偏低**的，留余量防止估算失误
2. 压缩这个动作本身要调一次模型，把旧消息全读一遍——这也要花空间

## 9. 痛点三：改错了想反悔

### 问题

Agent 改坏了 5 个文件，你想全部还原。

### 做法：检查点

在**任何会改文件的工具执行前**，先把该文件的「改动前内容」记下来。

`/rewind` 时按**逆序**还原——先改的后还原，这样同一文件被改多次也能正确回到最初状态。

有个细节：同一文件被改多次时，**只记录最早的那一次**。因为你要回退的是「这轮会话开始前的状态」，不是中间某个状态。

不落盘（只在内存里）是有意的：检查点只服务于当前会话，退出即失效。落盘会让磁盘慢慢堆满没人清理的备份。

## 10. 痛点四：一个 Agent 干所有事，上下文会脏

### 问题

让它「调研一下这个项目用了什么测试框架」——它读了 20 个文件，全是无关紧要的内容，这些全留在主对话历史里，把上下文撑满了。而你只想要一句结论。

### 做法：子 Agent

派一个**独立的临时 Agent** 去做调研：

```
主 Agent：「去查一下测试框架是什么」
    ↓
子 Agent：（自己的独立上下文，读 20 个文件）
    ↓
   返回一句：「用 bun test，配置在 bunfig.toml」
    ↓
主 Agent：只收到这一句，那 20 个文件的垃圾内容从没进过我的上下文
```

**关键设计有三条：**

1. **独立上下文**——子 Agent 的消息数组是独立的，读完即弃。主 Agent 只收到摘要。
2. **只读权限**——子 Agent 的工具列表里根本没有写文件和执行命令。**限制是在工具层面做的，不是在提示词里「请求」它别写。** 这个区别很重要：提示词约束可以被绕过（模型可能不听话），工具面没有那个工具就是物理上做不到。
3. **不能嵌套自己**——子 Agent 的工具列表里**没有「派生子 Agent」这个工具**。否则模型一旦调用就是无限递归，直接把程序跑死。

> 这里有个很典型的设计取舍：主循环里用 `deferred`（延迟加载，默认不发给模型以省 token）管理工具，但**不能**用 deferred 来阻止子 Agent 递归——因为 deferred 对主循环同样生效，会把子 Agent 能力从主循环里也摘掉。所以必须单独做一层工具面过滤。

## 11. 痛点五：等它干活的时候不知道它在干嘛

### 问题

Agent 在跑，屏幕上什么都不动。你不知道它在思考、在读文件、还是卡死了。

### 做法：结构化事件流

核心循环不直接画 UI，而是**发出事件**：

```
「我开始思考了」
「我打算调用这 3 个工具」
「工具 A 开始执行」
「工具 A 完成，输出是...」
「模型回复完毕」
```

UI 层订阅这些事件来渲染。**核心循环完全不知道 UI 长什么样。**

这带来的好处是同一套内核能服务三种场景：


| 场景                   | 怎么用                        |
| ------------------------ | ------------------------------- |
| 交互式终端             | 渲染成面板、spinner、工具卡片 |
| `--output-format json` | 把事件聚合成 JSON 给 CI 消费  |
| 管道 / 非 TTY          | 退化成纯文本，没有动画        |

**另外一个隐藏的好处**：如果核心循环自己打印 UI，那它就没法在测试里跑了。事件流让核心逻辑可以脱离终端被完整测试。

---

## 12. 痛点六：有些操作不该问，但必须可控

### 问题

你让它「一直改到测试通过为止」。它说「好的」，然后跑了 3 次就停了——因为它觉得自己做完了，但实际测试还挂着。

### 做法：目标评估器

`--goal <条件>` 模式：主循环跑完一轮后，**另起一次模型调用**专门判断目标达成了没：

```
主 Agent 干完活
    ↓
评估器：「条件是『测试全通过』，当前状态是... → 未达成，因为 auth.test.ts 还有 1 个失败」
    ↓
主 Agent：带着这个原因继续干
```

**为什么不用同一个模型顺便判断？** 因为「干活的」和「检查的」应该是两个独立判断。让执行者自己打分，它倾向于说「我干完了」。

**死循环刹车**：如果评估器发现条件**永远不可能达成**（比如条件是「让这个文件不存在但同时保留内容」），它会返回 `impossible`，主循环停止。没有这个刹车，无人值守模式会一直烧钱。

---

## 13. 痛点七：中断响应要快

### 问题

它正在跑一个 5 分钟的命令，你发现方向错了想停下来。

### 做法：AbortSignal 贯穿全链路

按 `Esc` 会同时做三件事：

1. 取消正在飞的 HTTP 请求
2. 杀掉 `run_shell` 起的子进程
3. 让正在等待的重试退避立刻返回

**一个容易忽略的细节**：重试的等待也必须响应中断。否则用户按了 Esc，程序还在傻等那 2 分钟的退避，表现就是「按了没反应」。

## 14. 和 Claude Code 的对比

现在你已经理解了所有核心机制，可以看清两者的关系了。

### 先说结论

**B Code 在架构思想上和 Claude Code 高度一致，在工程选择上有明显取舍。**

这不是「模仿」，而是**同一个问题的正确答案会收敛到相似的形状**——就像所有数据库都有 B+ 树，不是互相抄。

### 逐项对比


| 维度           | Claude Code    | B Code                    | 说明                                                |
| ---------------- | ---------------- | --------------------------- | ----------------------------------------------------- |
| **核心循环**   | 相同           | 相同                      | 都是「模型决定循环转不转」                          |
| **工具系统**   | 内置 + MCP     | 内置 + MCP                | MCP 协议两边都支持                                  |
| **权限模型**   | 多档模式       | 四档模式                  | 思路一致，B Code 明确区分「危险命令」和「敏感命令」 |
| **上下文压缩** | 自动压缩       | 分级压缩 + 文件指针       | B Code 用文件缓存解决「压缩后失忆」                 |
| **子 Agent**   | 支持           | 支持，工具面独立          | B Code 强制只读 + 禁止嵌套                          |
| **持久化记忆** | 有             | 有（项目隔离）            | 召回策略不同，见下                                  |
| **技能系统**   | 支持           | 兼容其目录格式            | B Code 可直接读 `~/.claude/skills`                  |
| **Hooks**      | 支持           | 兼容其协议                | 事件名、退出码语义一致                              |
| **模型后端**   | 仅 Anthropic   | Anthropic + OpenAI 兼容   | B Code 可接国产模型 / 自建                          |
| **UI 技术栈**  | 闭源           | OpenTUI（开源）           | 见下                                                |
| **分发方式**   | npm（需 Node） | 单文件可执行（零依赖）    | 见下                                                |
| **自主循环**   | 有             | 有（`--goal` / `--loop`） | 都靠独立评估器判断                                  |

### 几个值得展开的差异

#### 1. 模型后端：这是最实际的差别

Claude Code 只能用 Anthropic 的模型。B Code 支持 OpenAI 兼容格式——意味着你可以接 DeepSeek、通义、本地部署的模型等等。

**这个设计带来的复杂度**：两家的消息格式、工具调用格式、流式响应格式都不同。B Code 的解法是「内部统一用 Anthropic 形状，边界处转换」——这个决定让主循环保持了干净。

#### 2. 记忆的召回策略

Claude Code 的记忆召回更复杂。B Code 的选择是**纯确定性关键词重叠打分**：

- 拿当前查询跟记忆的标题、描述、正文做词集重叠
- 算个分，取前 3 条注入 system prompt

**为什么不用向量检索？** 三个理由：快（不用调 embedding API）、省（不花钱）、可预测（同样的输入永远同样的结果，好调试）。代价是语义近似的召回会弱一些。

代码里留了接口抽象，将来换向量库是替换一个实现类的事。

## 15. 如果让你来写，建议的顺序

从零开始的正确顺序（也是 B Code 实际的演进路径）：

```
第 1 步  while 循环 + 一个 read_file 工具
         → 能跑通就证明了核心原理

第 2 步  加 write_file + run_shell
         → 但此时必须立刻加权限确认，否则不能给人用

第 3 步  加流式输出 + 事件流
         → 否则用户体验是"卡死"

第 4 步  加工具结果截断 + 上下文压缩
         → 否则长对话必然崩溃

第 5 步  加 system prompt 约束
         → 否则模型行为不稳定

第 6 步  加检查点
         → 否则改坏了没法收拾

在此之后才是：子 Agent、记忆、技能、MCP、自主循环
```

**最后四样都是「锦上添花」，前六步是「不做就不能用」。** 很多项目倒在第三步之前——因为前两步做完觉得很酷，直接跳过权限去做花哨功能了。

## 16. 几个值得记住的教训

这些是开发过程中真实踩过的坑，对想自己实现的人应该有用：

### 1. 剪贴板这类系统能力，每个平台都是独立工程

macOS 用 `osascript`，Linux 用 `xclip` / `wl-paste`，Windows 用 PowerShell + .NET 的 `System.Windows.Forms`。

Windows 还有额外的坑：`Clipboard` 是 STA COM 组件，而 PowerShell 7 默认以 MTA 启动，不显式加 `-STA` 就直接抛异常。

**教训**：Windows 上失败的表现是「什么都没发生」，所以必须有明确的探测和降级路径，不能靠 try/catch 吞掉就完事。

### 2. 死循环的种子往往在「好心」的设计里

- 子 Agent 能派生子 Agent → 无限递归
- 压缩导致文件内容丢失 → 模型重读 → 又触发压缩
- 目标评估器永远返回「未达成」→ 无限烧钱

**教训**：每个「循环」和「自动重试」的机制旁边，都必须有一个明确的刹车。B Code 里分别是：工具面过滤、文件指针缓存、`impossible` 判定。

## 17. 结语

回到最开始那个四行的循环。

B Code 那 1.2 万行代码，本质上都是在让这四行能在真实世界里可靠运行：

- 模型会犯错 → 需要权限
- 上下文会满 → 需要压缩
- 用户会等急 → 需要流式
- 改坏要能退 → 需要检查点
- 任务太杂 → 需要子 Agent
- 无人值守 → 需要独立评估器

**每加一个模块，都应该能回答「它解决了哪一个具体问题」。** 回答不上来的，大概是过度设计。

如果你想读代码，建议就从这个循环开始（`src/agent.ts` 里搜索 `while`），然后顺着「它调用了谁」一路看下去——整个项目的结构会自己展开。
